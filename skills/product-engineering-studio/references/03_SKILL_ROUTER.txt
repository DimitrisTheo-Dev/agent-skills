SKILL ROUTER
Reference index, not an installed skill pack.
Use the installed version's actual instructions and dependencies. Upstream descriptions guide
selection; they do not establish local capabilities.

DEFAULT
Choose one main procedure for the current problem. Add a specialist only for a distinct concern.
Required helper skills remain required. Avoid running a full product, design, architecture and
review pipeline on every small change.

OPTIONAL SKILLS
Skills named below that are not in this pack are optional. This pack ships
product-engineering-studio, vibe-ui, ui-quality-gate, product-readiness and landing-page-design.
Vibe UI carries the UX pattern, typography, color, geometry, motion and interface-writing
references; this Studio carries the design playbook; Product Readiness carries agent readiness. If a
skill is missing, do the step directly using this file.

CORE CHOICES
- Delivery baseline, changed product commitments or release readiness: product-readiness when
  accessible. Reuse the existing acceptance record and UI Quality Gate evidence. Use its agent
  readiness reference for detailed agent requirements. If unavailable, record applicable checks and
  remaining unknowns within Studio.
- Unclear feature inside a repository: grill-with-docs. Resolve scope; cap the initial question
  round. It uses grilling and domain-modeling.
- Idea clarification outside a repository: use the intake procedure here; grill-me is optional if
  actually installed.
- Ambiguous terms or roles: domain-modeling. Define the terms affecting this change.
- Interface or module design: codebase-design. Prefer a simple caller contract.
- Defined behavior: tdd. Agree the meaningful testing boundary and build in small behavior steps.
- React/Next.js performance or changed data/render paths: use the installed Vercel React Best
  Practices selectively and React Doctor diagnostics when the pinned tool is available. Product
  Readiness carries portable fallbacks and quality budgets. Prioritize waterfalls/bundles, preserve
  the actual framework and state library, and keep tool scores distinct from runtime behavior.
- Difficult reproducible failure: diagnosing-bugs. Find evidence before fixing.
- Unsettled flow or interaction: use an installed prototype skill that fits the question. Check its
  source and scope because helpers with this name can cover logic, UI variants, or both. Use a small
  disposable view in the existing stack when that answers the question directly.
- Finished code: code-review. Its documented default uses a committed range and a supplied base. A
  scope override must be explicit and honored; otherwise snapshot the intended work before review.
  Include new files.
- Implemented UI before handoff: ui-quality-gate when installed. It owns ordered inspection,
  evidence and repair/recheck; vibe-ui owns design corrections. For a narrow fix, review its
  component and affected neighbors/states. Backend-only work skips this route. If unavailable, use
  Quality and Design and Creative Quality and name unverified areas. interface-review is an optional
  specialist, not a duplicate competing gate.
- Direction, implementation craft and character review: vibe-ui when accessible. Select brief, build
  or review mode to match the current task. During assessment, use review mode with an independent
  worker when permitted; otherwise label self-review. Keep correctness, usability, craft and
  character distinct.
- Accepted direction across workstreams, or repeated focus/shift/hit-target defects: the design
  playbook (references/design-playbook.md). Use its contract, bounded packets and measured proof
  inside the current slice. It does not reopen accepted art direction or replace Studio's
  integration ownership or the final UI Quality Gate. A single ordinary edit does not need the extra
  workflow.
- Single design concerns: vibe-ui, which carries references for task representation and flow,
  reading and type roles, palette and contrast, spacing and component geometry, feedback and
  transitions, and interface copy. Choose by the decisions still open.
- Advanced color ramps/gamut: better-colors is an optional helper when accessible and a concrete
  need remains; vibe-ui's color reference keeps the product role decisions.
- Interface copy, empty states, errors and voice: vibe-ui's interface-writing reference. For
  persuasion and page narrative, landing-page-design when accessible.
- Implementation craft: use Emil's animate or gestures for motion mechanics, mobile-native for
  mobile browser behavior, and break-ui for content stress tests when installed. Feed their
  observations into the existing review. For recurring corrections, learn-taste can retain the
  user's confirmed reasons in the existing design record. Check installed instructions and keep each
  helper within the requested scope. See Tool Selection for sources.
- Sensitive data/auth flow: local vibe-security where available, plus applicable OWASP-backed checks
  in Product Readiness or this Studio's quality guide. Verify legitimate and denied object/tenant
  operations at the server boundary. A clean dependency or frontend scan does not establish
  authorization.
- Collections, queries, expensive work or scaling requests: use Product Readiness's
  workload/query-count checks when accessible; otherwise inspect bounded queries, batching, plans,
  connection/fan-out limits and cache ownership here. Promise.all does not remove N+1 work. Add
  infrastructure only for a measured or explicit workload need.
- SQL/Postgres work: supabase-postgres-best-practices when installed. It is a database guide, not
  evidence that Supabase is the chosen platform.
- Browser/frontend detail: modern-web-guidance only for the specific concern and actual runtime.
- Context transfer: handoff when the session needs a durable summary.

LARGER WORK
to-spec, to-tickets and wayfinder are conditional tools for work that outgrows a single small
session. Do not create a ticket ceremony for a one-hour change. setup-matt-pocock-skills is a
deliberate repository setup step, not a task to repeat on every request.

T3 TSTACK, OPTIONAL
sol-loop provides a Sol review route; rehearse its actual prerequisites. For Sprint use, explicitly
request one round or a five-minute budget rather than its broader upstream default. Missing provider
access means use a normal review.
council adds cross-provider review overhead. full-stop and full-send perform release/PR workflows.
Keep them out of ordinary local iterations; select shipping only when the user requests it.

GSTACK, OPTIONAL
office-hours can challenge product framing. plan-ceo-review can hold or reduce scope. Use the
business lens when product uncertainty is the bottleneck.
Upstream documentation checked on 2026-11-07 says standalone plan-eng-review was removed on November
6; architectural review remains within autoplan. Do not prescribe obsolete commands. Verify the
installed version. Do not preload autoplan or nest gstack shipping inside another execution loop.

FALLOW, OPTIONAL
Use for structural questions in existing JS/TS code: changed-code risk, duplication, cycles,
complexity or unused code. Analyze the relevant diff and inspect findings before removing code. It
complements runtime checks.
A skill install does not establish that the Fallow executable exists. Check prerequisites. Avoid
unsolicited hooks, CI reconfiguration or broad cleanup.

MOBBIN
Use the connected tool for one specific screen, flow or section. Follow its current search
instructions. If unavailable, state that and proceed with the supplied references and own design
rationale. Never invent returned references.

INVOCATION
Invocation syntax depends on the host: `/name` or `/plugin:name` in Claude Code, `$name` in Codex.
Check the host before naming a command.
Do not interpret a suggested command in a reference as permission to install, publish or change
account settings.
