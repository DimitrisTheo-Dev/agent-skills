# Principles and work packets

## One-page principles

Adapt these fields in the project's existing design record. Values come from tokens, not a second
stylesheet hidden in prose.

| Field | Record |
| --- | --- |
| Outcome | Person, task, successful result, critical dependency |
| Identity | Accepted direction, authentic assets and expressive zones |
| Sources | Token path, component primitives, references and translation |
| Hierarchy | Main action, repeated facts to remove, information that must remain |
| Interaction | Frequent action, feedback, pending/confirmed/error behavior |
| Constraints | Supported viewports, input modes, language and accessibility needs |
| Corrections | Exact owner phrase, scoped interpretation, reproducing check |
| Delivery | Current slice, shared-file owner, next integration checkpoint |

For a calm interface, favor stable targets, quiet focus, restrained repetition and truthful status.
Choose actual durations and ring treatment from the product contract; “all motion under 300ms” and a
universal 2px ring are not prerequisites.

## Bounded worker packet

```text
Outcome: one observable part of the current slice
Baseline: revision and actual project commands
Context: accepted direction, principles path, accessible references
YOU OWN: exact paths or a genuinely separate module
SHARED OWNER: tokens, state, contracts, manifests and lockfiles
DO NOT TOUCH: sibling work and shared files outside your ownership
Change: current behavior/text, target behavior and known cause or uncertainty
Prove it: input/state, expected outcome, measurement and capture to return
Budget/checkpoint: next useful boundary; report blockers before it
Return: changed paths, observed evidence, limits and proposed shared changes
```

Keep instructions proportional. Include only the few relevant specialist names, plus required
dependencies. Verify their actual availability; an external skill name is not a bundled resource. A
lead may implement a bounded task while retaining integration capacity. “Coordinator never edits UI”
is not a requirement.

## Runtime ownership

- Record whether workers share a checkout. In one checkout, designate shared files and serialize
  installs/builds that use the same mutable output. Separate branches alone do not isolate working
  files.
- Use separate worktrees and actual dependency installs when isolation is needed. Avoid symlinking
  mutable dependency/build directories across concurrent work. Offline installation is appropriate
  only when the cache has the required versions.
- Give each running server an owned port and each capture/build a private output path. Reuse a
  healthy server when suitable. Stop only processes started and owned by this task; never free a
  port by killing an unknown session.
- Wait for a meaningful rendered locator and the required loaded state before operating the page.
  Polling/streaming apps may never reach network idle. A successful HTTP response alone does not
  prove hydration or interactivity.
- Before renaming visible labels, inspect affected accessible-name selectors, tests and sibling
  contracts. Report the old and new terms to the integration owner.
- After interruption, inspect the actual checkout, processes and evidence, then resume from the
  smallest useful checkpoint. Preserve unrelated edits. Do not restart productive work just to
  change the staffing plan.

## Integration return

The lead checks the diff, confirms shared contracts, runs the slice on the integrated candidate and
opens the evidence. Recheck affected capture provenance after merges. Return one concise status, not
a pasted transcript from each worker. Keep one readiness record with distinct design, implementation
and live-service evidence.
