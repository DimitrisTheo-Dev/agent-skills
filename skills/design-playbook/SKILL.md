# Design playbook

Turn a chosen direction into a coherent, working flow. Keep the product outcome, the owner's
corrections and observed evidence together. Use the same process with one executor or permitted
workers. A calm native feel is a possible brief, not the compulsory style of every product.

## 1. Set the boundary

Read the request, project instructions, current design record and governing components/tokens.
Identify one user outcome, the critical state transition, the candidate revision and available time.
Review-only stays read-only; a focused repair keeps the accepted design. Backend-only work exits
this workflow.

When direction is unsettled, let the installed Vibe UI own exploration; otherwise choose a bounded
comparison from the actual audience and content. Once a direction is accepted, carry it forward. For
a timed demo, identify the earliest real dependency check and reserve time for integration and
rehearsal before adding optional surfaces.

**Done when:** the scope, main action, actual success condition, relevant states and unresolved
dependency are explicit. “Build passes” is not the user's success condition.

## 2. Make one contract

Convert supplied references into words: relationship to preserve, product-specific adaptation, and
elements excluded by the brief. Give workers the accessible images as well as the description when
their tools support them. Do not assume image access in either direction.

Resolve literal values in the existing token/component source: semantic colors, type roles and
wrapping, spacing/density, radii by class, elevation, focus, motion and responsive behavior. Choose
reversible values from the brief and inspect them; ask for exact values only when an unresolved
brand requirement makes that necessary.

Keep DESIGN.md as a short decision index pointing to implementation values. Record identity zones,
exceptions and ownership there. Adapt the one-page principles template in [work
packets](references/work-packets.md); use the existing record instead of creating parallel
documents. Load [the Faceful example](references/look-faceful.md) only for an explicit request for
that look or a relevant reference comparison.

**Done when:** the first slice can be built from concrete values, the accepted direction has one
source, and each shared file has one owner.

## 3. Deliver an owned slice

Use Product Engineering Studio for product scope and integration when installed. Load only
specialists needed by the current problem: UX patterns, typography, color, geometry, motion or copy.
Keep one lead and one final quality gate. Other skills are optional helpers; this package contains
the minimum workflow when they are absent.

Default to one executor. Delegate only if tools and instructions permit, useful tasks are
independent, shared contracts are settled, and integration fits the remaining budget. Give each
worker the bounded packet in [work packets](references/work-packets.md). The lead owns tokens,
shared state/contracts, dependency changes, integration and the final claim. Workers propose shared
changes instead of editing outside their ownership.

Prove the risky dependency with real output early. For a media workflow, a queued job or successful
upload of a non-media test object does not establish playable output. Check required
configuration/migrations, produce the actual artifact and pass it to the next stage in an authorized
environment. Keep fixtures visibly separate from live results. A blocked provider reduces the next
slice; it does not justify making more dependent UI.

**Done when:** the integrated slice demonstrates its promised outcome, or a specific blocker and
useful bounded fallback are recorded. Worker completion alone does not close integration.

## 4. Inspect and correct

Capture the relevant wide and narrow layouts, inspect the images, then operate the transition. Add
320px reflow and intermediate breakpoint checks when the change affects them. Start with task
clarity and hierarchy, then inspect component craft. Apply [craft
recipes](references/craft-recipes.md) only to observed defects; retain the product's chosen values.

Translate each owner correction into **their words → scoped rule → reproducing check**. “Too much”
needs a named repeated fact or competing action; “no wobble” needs a named element and transition.
Preserve necessary labels, error recovery, consent and approval boundaries while simplifying. After
two unsuccessful fixes to the same symptom, inspect a different cause: cascade, clipping ancestor,
hit region, state ownership or stale preview.

**Done when:** the changed flow and affected neighbors have been inspected, and each material defect
is closed by a recheck or explicitly remains unresolved.

## 5. Prove the candidate

Use [verification](references/verify.md) for scoped measurements, focus clipping, hit targets,
shifts, loading, contrast and browser coverage. UI Quality Gate owns the final inspection when
installed; give it this evidence instead of opening a second loop. Otherwise apply the verification
reference directly.

Report source revision, runtime, route/state, fixture/live status, method, observed result and
limitations. Keep component displacement, page CLS, automated accessibility findings and visual
judgment separate. A requested 0px result is a target until measured; unavailable coverage stays
unverified. Inspect artifacts before repeating a worker's claim. Sanitize public evidence before
committing it.

**Done when:** required outcomes have current evidence on the integrated candidate, with no
unresolved major/blocking defect. A deadline can end work with a partial result; it cannot turn
missing evidence into a pass.

## 6. Close the loop

Reconcile the design record with shipped tokens and behavior. Retain decisions, reasons and accepted
exceptions; replace stale value copies with source paths. Capture the next action and blockers for
interrupted work so it can resume without restarting the brief.

Store product-specific taste in the project. Promote a recurring, transferable correction into the
relevant specialist and its check; keep this skill focused on the delivery process. Read [the
Faceful history](references/faceful-history.md) when adapting the lessons or evaluating which claims
the evidence supports.

**Done when:** the contract describes the candidate, the useful correction is retained once, and the
handoff distinguishes implemented, locally verified and verified live behavior.
