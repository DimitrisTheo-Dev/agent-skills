# Conditional pattern decisions

The tables are a retrieval aid, not a ranking of fashionable patterns. Select from the task, content and current behavior. A pattern needs a reason to beat the existing structure.

| Situation | Consider | Useful condition | Prefer another structure when | Check the result |
| --- | --- | --- | --- | --- |
| People choose among visually distinct objects | Thumbnail cards or image-led rows | An authentic preview helps recognition or communicates outcome | Images are arbitrary, repetitive or hide comparison attributes | Find a particular object with real images and a missing image |
| People compare many homogeneous records | Aligned list or table | A few repeated attributes determine choice; sorting/bulk actions matter | Unique visual identity is the main decision factor | Compare multiple records without opening each |
| People resume ongoing work | A concise resume item plus organized collection | The next unfinished task is known and useful | Recency is not the user's priority or evidence is unreliable | Resume correctly and still discover other work |
| A long form has dependencies or distinct stages | Steps with persistent summary/preview | Later choices depend on earlier ones and a meaningful intermediate outcome exists | A few independent fields fit comfortably or experts edit across sections | Back/edit without losing values; see commitment before final submit |
| A short form looks oversized | Single page with stronger grouping and optional sections | Inputs are independent and completion is quick | Conditional branches create real complexity | Complete on a phone without unnecessary navigation |
| Choices alter a visible output | Editor plus live preview or sample result | The preview is truthful and helps a decision | It implies backend results that are not available or steals needed input space | Change an input and recognize its actual effect |
| Too many options fill the screen | Searchable selection, categories or progressive disclosure | Volume exceeds useful scanning and choices have recognizable labels | A few frequent choices benefit from staying visible | Discover, select, edit and remove with keyboard and touch |
| Frequent details interrupt a collection | Master-detail or detail panel | People inspect multiple records while retaining list context | Tasks need deep focus, URL navigation or more width than a panel offers | Preserve selection, scroll and route state; adapt to mobile navigation |
| A page mixes unrelated work | Task-based sections or navigation | Distinct jobs have distinct entry points | Separation would hide tightly coupled decisions | Name the sections without internal implementation jargon |
| Onboarding asks for everything | First-value path with deferred setup | Some fields/integrations are unnecessary for the first real outcome | Prerequisites are genuinely required for a safe or meaningful result | Reach real value, then return to incomplete setup |
| An empty surface gives no direction | A contextual starter, truthful example or direct creation path | The next useful action is known | A fake populated demo could be mistaken for real user data | Start work without decoding a tutorial |
| Search produces no useful result | Clear query context, removable filters and recovery | Active constraints or alternative wording can help | A loading error is being misrepresented as no results | Distinguish empty, filtered, unavailable and failed |
| Dense monitoring has many equal metrics | Task-prioritized overview plus drill-down | Some changes require attention more than others | Users need arbitrary cross-column comparisons visible together | Identify the actionable exception without reading every tile |
| Destructive or consequential action is easy to trigger | Clear consequence, proportionate confirmation or undo | Impact and recoverability justify the interruption | Every routine action is being slowed by a modal | Understand consequence and recover where supported |
| Experts repeat actions frequently | Visible efficient controls and optional shortcuts/command search | Actions have stable names and repetition justifies acceleration | A command palette would conceal the only discoverable path | Complete with pointer and keyboard without memorization |
| A marketing page does not explain value | Clear offer, concrete product evidence, proof and next action | The visitor is deciding whether to engage | It is a daily workspace whose user already understands the product | Explain the offer from the first screen without reading every paragraph |

## Worked decisions

**Learning collection.** A small set of creative lessons with distinctive outputs can use real thumbnails, a clear title, progress and a resume action. Keep card chrome quiet; an arbitrary icon per lesson adds little. A library of hundreds of similarly named compliance lessons may work better as searchable rows with duration and completion columns. The lesson topic alone does not select cards.

**Creation flow.** An author choosing source material, configuring output and reviewing the result may benefit from three stages with a persistent summary. A title, date and visibility form usually benefits from one compact page. Step count follows dependencies, not the aesthetic appeal of a progress bar.

**Preview.** A style editor can update a truthful local preview immediately. A generated result that needs a server should show a labeled sample or an honest pending state until the real output exists. Do not build fake certainty into a beautiful preview.

**Responsive detail.** Wide layouts can retain a list beside details. Narrow layouts may navigate to a detail view with an explicit back path, restored selection/scroll and a shareable route. Merely squeezing the same two columns changes the experience for the worse.

## Avoid formulaic upgrades

A card needs meaningful object boundaries or content relationships. A step needs a task boundary. A preview needs decision value. A drawer needs retained context. A badge needs a stable, useful meaning. Remove or revise a pattern that adds ceremony without improving the task.

Preserve learned behavior in mature products unless there is evidence and scope for change. Improvements can be better ordering, language, defaults or in-place feedback without changing the page's architecture.
