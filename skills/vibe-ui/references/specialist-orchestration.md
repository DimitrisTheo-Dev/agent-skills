# Coordinate five specialists

Vibe UI owns the coherent design. Specialists resolve bounded decisions; they are not five independent art directors. Studio remains the entry point for full product work. The user should not need to select or invoke these helpers manually.

## Route only what is unsettled

| Concern | Owner | Return |
| --- | --- | --- |
| Information order, collection representation, forms, navigation and first value | ui-ux-patterns | Chosen structure, conditions, tradeoff, responsive journey and states |
| Type identity, roles, readability and text rhythm | ui-typography | Actual family/role system, wrapping and language constraints |
| Palette construction, semantic meaning and contrast | ui-color | Contextual palette, role map, area distribution and checked pairs |
| Density, spacing, corners, borders, outlines and elevation | ui-geometry | Concrete tokens, component geometry and optical exceptions |
| Feedback, transitions, async states and supported haptics | ui-motion | Interaction/state specification, reduced motion and runtime evidence |

Check the actual installed instructions before relying on a helper. An unavailable helper does not authorize installation or block useful work: use the task brief, existing system and local craft/QA guidance, then name any unverified coverage.

- **Fix:** use the existing contract, invoke only the affected specialist and review neighboring effects. No new art direction, palette menu or full five-part report.
- **Extend:** inherit established decisions; invoke the owners of new or conflicting choices. Check the completed slice through one gate.
- **Shape:** resolve all five concerns. Start with the user's task and representation, jointly choose type/color character, settle geometry and specify interactions as the first flow is built. Revisit coupled decisions together rather than passing a flawed layout through a styling waterfall.

A palette or font concern can be handled directly without Studio. Standalone helpers give their relevant evidence and limitations; they do not automatically summon every sibling.

## Share one contract

Use the existing design record or one compact DESIGN.md when implementation/artifact creation is authorized. Review-only returns the record in the response. Store actual implementation values in governing tokens/components, referenced by path; avoid duplicate token files.

Record only consequential decisions:

- **Intent:** person, task, frequency, screen job, desired character and constraints.
- **Structure:** information/action order, chosen pattern, why it fits and what would change the choice.
- **Typography:** chosen direction, available families, role metrics and wrapping/language rules.
- **Color:** chosen construction, hue rationale, surface/action/status roles, proportions and measured pairs.
- **Geometry:** density, spacing relationships, radii/boundaries, shared dimensions and deliberate exceptions.
- **Interaction:** affected families, trigger/feedback/pending/result/recovery, motion values and reduced-motion alternative; haptic scope if supported.
- **Evidence:** selected/rejected direction, inspected states, unresolved findings and current candidate.

A localized change updates only its section and affected evidence. Preserve accepted user preferences with their reasons and product scope. Do not make the user answer a taste questionnaire on each task.

## Keep alternatives bounded and comparable

At Shape depth, use two or three coherent whole-screen directions total. Typography and color shortlists feed those same directions; do not render a Cartesian product of five specialties or ten type profiles. Reuse the same content, state fixtures and responsive captures.

At Extend depth, compare only the consequential unresolved choice. At Fix depth, inspect before and after. Stop generating alternatives when evidence supports a choice. Spend further effort on observed deficiencies, not novelty for its own sake.

## Reconcile conflicts explicitly

The user's requirements, task, accessibility and technical constraints govern the choice. Vibe UI resolves conflicts within that context:

- A display face that clips should trigger a measure/layout or font-role adjustment, not arbitrary text shrinking.
- A bright brand field can coexist with a neutral action if that gives the action better hierarchy.
- A compact row can retain a larger nonoverlapping hit region.
- A sticky preview can become an accessible summary on narrow screens.
- A lively transition must not delay input or make pending work look confirmed.

Each specialist changes its own concern and reports cross-concern consequences. Shared files need one integration owner; helper use does not imply parallel workers.

## One final review

UI Quality Gate inspects the complete result, compares it to the shared contract and challenges the contract when it fails the task. It routes fixes to the relevant owner, then rechecks affected states. Specialists do not each start another gate. Passing token checks establishes consistency; passing runtime checks establishes specific behavior; neither alone establishes character.

Cover each affected component family and each exceptional instance/state. Reuse evidence for genuinely identical implementations. This is comprehensive inspection without a separate report for every repeated button.
